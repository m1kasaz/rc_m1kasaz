# AI 使用说明

> 作业要求：说明 AI 在哪些关键地方提供帮助、AI 给出过哪些未采纳的建议、哪些关键决策是自己做出的及原因。

## 1. AI 提供关键帮助的地方

1. **问题域定位**（v2.0 关键转折）：AI 初版 PRD 停留在功能罗列，被评审指出"空洞"。人工给出两个拆解方向后（① 该组件面向写操作而非读接口；② 核心问题是 HTTP 写请求在分布式系统中的可达性），AI 据此将 PRD 重写为「失败模式枚举 + 两将军问题推导 + 四决策」的问题驱动结构。
2. **架构模式对比**：AI 列举了持久化队列、内存队列 + 补偿、消息队列三种受理/投递解耦模式及其取舍，为决策提供完整对比面。
3. **图纸生成**：流程图与时序图（mermaid）由 AI 起草，人工确认语义后微调。
4. **用例矩阵展开**：以技术文档的接口定义、状态机、失败分类矩阵为输入，AI 批量展开成具体用例，人工做覆盖度评审并补充 3 条。

## 2. AI 给出但**未采纳**的建议

| AI 建议 | 未采纳原因 |
| --- | --- |
| Kafka + 消费者组作为核心队列 | 单机 MVP 用 SQLite 退避列即可满足"持久化+领取+延迟"三要素；Kafka 部署与语义成本远大于收益（详见技术文档 §7） |
| Exactly-once 投递 + 去重表 | 跨外部系统边界物理不可达，at-least-once + 幂等键是更诚实的语义 |
| BullMQ + Redis 作为任务框架 | Redis 默认持久化不满足"受理即事务落库"的要求 |
| 「HTTP 2xx 即送达」作为唯一判定（AI 初版默认） | 2xx 只证明网关收到，不证明业务生效；人工评审明确要求业务级回执（D1） |
| ack 超时后自动无限重投 | 假送达场景（供应商已处理但回执丢失）下自动重投放大副作用；MVP 选择告警 + 人工，v1.1 受控重放 |
| NestJS 全家桶 | 对 MVP 过重，Hono 足够 |

## 3. 人工做出的关键决策及原因

1. **问题域拆解**（最重要的决策）：把需求锚定为"写操作可靠性 / HTTP 写请求在分布式系统中的可达性"，并用两将军问题推出"at-least-once + 幂等键是可靠性上限"这一基础结论。此拆解由人工提出，直接决定了 v2.0 的全部结构。
2. **D1 送达判定 = 业务级回执**：选择供应商回执回调而非 2xx 即送达。理由：作业核心诉求是"通知到达并生效"，仅 2xx 会系统性漏掉"网关成功、业务失败"的假送达。
3. **D3 长时故障 = 超长退避（覆盖约 4 天）+ 分级告警**：来自对内部通知业务时效容忍的判断——晚到与丢失的业务后果完全不同，因此拉长重试窗口、不轻言放弃；但保留死信作为诚实止损。
4. **D4 持久化强度 = 事务提交即返回**：可靠性投入与风险成正比，阶段②（受理后崩溃）概率远小于阶段③④，不值得为其付出确定性 fsync 延迟。
5. **MVP 边界收缩**（不做排序保证、模板引擎、凭证托管、实时回调业务方）：依据作业"更关注工程判断和取舍逻辑"的评估重点。
6. **测试范围裁剪**：性能压测、多实例、安全测试不进 MVP 用例集，AI 初稿倾向"求全"，人工按 MVP 边界裁剪；同时人工发现初稿遗漏崩溃恢复、退避抖动、ack 乱序三类用例并补充。
