# AI 使用说明

> 作业要求：说明 AI 在哪些关键地方提供帮助、AI 给出过哪些未采纳的建议、哪些关键决策是自己做出的及原因。

## 1. AI 提供关键帮助的地方

1. **需求拆解与文档骨架**：由作业 PDF 出发，AI 辅助将模糊需求拆解为 PRD → 技术文档 → 测试用例评审三阶段，并保证了后继文档对前继文档的可追溯引用。
2. **架构模式选型**：AI 列举了持久化队列、内存队列 + 补偿、消息队列三种受理/投递解耦模式及其取舍，为最终决策提供了完整对比面。
3. **图纸生成**：流程图与时序图（mermaid）由 AI 起草，人工确认语义后微调。
4. **用例矩阵展开**：以技术文档的接口定义、状态机、失败分类矩阵为输入，AI 批量展开成具体用例（含前置条件与预期），人工做覆盖度评审并补充 2 条。

## 2. AI 给出但**未采纳**的建议

| AI 建议 | 未采纳原因 |
| --- | --- |
| Kafka + 消费者组作为核心队列 | 单机 MVP 用 SQLite 退避列即可满足"持久化+领取+延迟"三要素；Kafka 部署与语义成本远大于收益（详见技术文档 §7） |
| Exactly-once 投递 + 去重表 | 跨外部系统边界物理不可达，at-least-once + 幂等键是更诚实的语义，避免误导调用方 |
| BullMQ + Redis 作为任务框架 | 引入 Redis 依赖，且 Redis 默认持久化不满足"受理即持久"的目标 |
| 回调业务方的 webhook 回执机制 | 作业明确业务方不消费返回值，回调引入双向耦合 |
| NestJS 全家桶 | 对 MVP 过重，Hono 足够 |

## 3. 人工做出的关键决策及原因

1. **投递语义定为 at-least-once**：这是语义层面的判断，基于"跨系统边界无分布式事务"这一事实，而非功能对比。
2. **MVP 明确排除的范围**（返回值透传、排序保证、模板引擎、凭证托管）：依据作业"我们更关注工程判断和取舍逻辑"的评估重点，主动收缩边界以换取每个保留项的设计深度。
3. **4xx 直接死信、其余退避**：失败分类策略来自对"重试是否有意义"的判断（可重试失败是暂时的，4xx 是确定的），而非 AI 给出的统一重试模板。
4. **测试范围裁剪**：性能压测、多实例、安全测试不进入 MVP 用例集，AI 初稿倾向于"求全"，人工按 MVP 边界裁剪。
