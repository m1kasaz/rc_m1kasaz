# PRD：企业内部 API 通知系统（NotifyHub）

> 版本：v2.0 ｜ 状态：已评审 ｜ 上游：AI Coding 作业《API 通知系统设计与实现》
> v2.0 变更：按评审意见重写 §2 问题分析，将需求锚定在「写操作可靠性」这一真实技术问题上；投递语义、回执机制、退避参数依据决策记录 D1–D4 落定。

---

## 1. 需求背景

### 1.1 业务背景

企业内部多个业务系统（广告引流注册、订阅付款、电商下单等）在关键业务事件发生时，需调用**外部系统供应商**提供的 HTTP(S) API 完成通知，例如：

- 用户通过第三方广告系统引流并成功注册后，通知对应的广告系统；
- 用户订阅付款成功后，通知 CRM 系统更改 Contact 状态；
- 用户购买商品后，通知库存系统进行库存变更。

### 1.2 现状痛点

| 痛点 | 说明 |
| --- | --- |
| 供应商 API 碎片化 | 各供应商请求地址、Header、Body 格式各不相同，每个业务系统各自对接，重复建设 |
| 可靠性无保障 | 外部 API 可能超时、失败、长期不可用。业务系统"发完即忘"，失败即丢失 |
| 关注点错位 | 业务系统**不需要关心外部 API 的返回值**，只要求通知"稳定、可靠地送达"，但现状把可靠性负担压在了业务方 |

### 1.3 问题定义

> 设计并实现一个**内部通知服务**：接收业务系统提交的外部 HTTP 通知请求，并尽可能可靠地投递到目标地址，将"如何可靠送达"的责任从业务系统收拢到单一服务内。

## 2. 问题分析：一次 HTTP 写请求的可达性

### 2.1 本质：这是一个写操作可靠性问题

需求中「不需要关心外部 API 的返回值」指明了该组件面向的是**写操作（fire-and-forget write）**，不是读接口。写操作可靠性的核心难点是**两将军问题**：

> 请求方永远无法区分「请求没送到」和「请求送到了，但响应丢了」。

由此推出一个不可回避的结论：

- 任何"超时即重试"的机制必然产生**重复请求**；
- 因此可靠性的上限 = **投递方重试（至少一次）** + **接收方幂等去重**；
- 「恰好一次」在跨系统边界上物理不可达，任何声称 exactly-once 的方案都必须拆解为这两半。

### 2.2 通知全链路的失败模式枚举

一次通知要真正"送达"，需经历 5 个阶段，每个阶段的故障模式与对策各不相同：

| 阶段 | 故障模式 | 后果 | 对策 |
| --- | --- | --- | --- |
| ① 业务系统 → NotifyHub | 网络中断、NotifyHub 不可达 | 通知未受理 | 业务方重试（同幂等键）→ **要求受理接口幂等** |
| ② NotifyHub 受理后 | 进程崩溃、断电 | 已回执 202 但通知丢失 | **先持久化后回执**（决策 D4） |
| ③ NotifyHub → 供应商 | DNS 失败、TCP/TLS 握手失败、连接重置、超时 | 未送达或送达未知 | 失败分类 + 退避重试（§2.4） |
| ④ 供应商收到后 | 返回 2xx 但内部业务处理失败；返回业务错误码 | **"假送达"**：HTTP 层成功、业务层失败 | **业务级回执机制**（决策 D1） |
| ⑤ 供应商长期不可用 | 持续 5xx/网络错误数小时至数天 | 任务积压、何时放弃 | 超长退避 + 告警（决策 D3） |

阶段 ④ 是容易被忽略、但恰恰最符合"可靠送达"业务语义的问题：**HTTP 2xx 只证明供应商的网关收到了请求，不证明 Contact 状态真的被改了**。本次评审明确将其纳入系统职责（见 §2.4 决策 D1）。

### 2.3 核心问题陈述

> **如何保证一次 HTTP 写请求，在双方系统都可能故障、网络可能中断、响应可能丢失的分布式环境中，最终被对方确认处理？**

拆解为四个子问题，分别对应四个关键决策：

| 子问题 | 决策 |
| --- | --- |
| Q1 「送达」如何判定？（2xx 还是业务确认？） | **D1：业务级回执**（供应商回执回调 NotifyHub；无回执能力的供应商降级为 2xx 即送达，按供应商配置） |
| Q2 重复请求如何处理？ | **D2：at-least-once + 幂等键**，假设下游通知语义幂等或可去重 |
| Q3 供应商长期不可用怎么办？ | **D3：超长退避（覆盖数天）+ 分级告警**，重试耗尽才进死信 |
| Q4 受理回执与持久化的顺序？ | **D4：事务提交后才返回 202**，进程崩溃不丢已受理通知 |

### 2.4 关键决策记录

**D1 送达判定 = 业务级回执**
HTTP 2xx 仅为"已投递"（DELIVERED），供应商业务处理确认（ACK）才是"已送达"（ACKED）。
实现：NotifyHub 提供回执接收接口 `POST /v1/notifications/{id}/ack`，由供应商或对接方在业务处理完成后调用；每供应商配置 `ack_mode: callback | http_2xx`。
影响：状态机引入 `DELIVERED / AWAITING_ACK / ACKED / ACK_FAILED` 态；无回执能力的供应商按降级策略处理。
理由：作业的核心诉求是"通知到达并生效"，仅 2xx 会系统性漏掉阶段④故障，与需求目标直接冲突。

**D2 投递语义 = at-least-once + 幂等键**
重试必然产生重复（两将军问题），由幂等键（`idempotency_key`，业务方生成、全局唯一）保证同一业务事件不产生副作用。
理由：通知类写操作（改状态、同步数据）语义上幂等；恰一次不可达（§2.1），不伪装。

**D3 长时故障 = 超长退避 + 分级告警**
退避序列 `1m → 5m → 30m → 2h → 6h → 24h → 72h`（共 7 次重试，覆盖约 4 天故障窗口），叠加 ±20% 抖动。
告警分级：`attempts ≥ 4`（约 2 小时后仍在重试）触发 warning；进死信触发 critical。
理由：内部业务通知的时效容忍是天级（同步库存晚一天与丢失一天，业务后果完全不同）；无限重试会放大故障并阻塞队列，死信+人工是诚实的止损边界。

**D4 持久化强度 = 事务提交即返回**
受理在 SQLite 事务提交（WAL 模式）后返回 202。不追求每次 fsync：进程崩溃丢失的是操作系统页缓存窗口内的数据，概率极低，而每次 fsync 的写延迟代价是确定性的。
理由：可靠性投入与风险成正比——阶段②的概率远小于阶段③④，不值得为其付出确定性延迟。

## 3. 需求目标

### 3.1 功能目标（MVP）

1. **通知受理**：统一 HTTP API 接收「目标地址 + 请求格式 + 通知内容」，同步校验、事务持久化后返回受理回执（202）。
2. **可靠投递**：at-least-once 语义异步投递；失败按分类策略（§2.2 阶段③）退避重试。
3. **送达确认**：支持业务级回执（D1），供应商确认后通知进入终态 `ACKED`；支持按供应商降级为 2xx 即送达。
4. **状态可观测**：业务系统可查询通知生命周期状态（含投递进度与回执状态）。
5. **幂等受理**：同一 `idempotency_key` 重复提交不产生副作用。

### 3.2 非功能目标

| 维度 | 目标（MVP） |
| --- | --- |
| 受理持久性 | 202 回执对应的数据已事务落盘，进程崩溃不丢（D4） |
| 送达时效 | 供应商健康时秒级送达；故障时按 D3 退避，最长覆盖约 4 天 |
| 可观测性 | 各状态数量、attempts 分布、死信量、AWAITING_ACK 滞留时长可查询/告警 |
| 性能 | 单实例 ≥ 100 TPS 受理峰值（设计余量，非验收线） |

### 3.3 状态机（对外语义）

```
PENDING ──claim──▶ IN_FLIGHT ─┬─ 2xx ─▶ DELIVERED ──(callback 模式)──▶ AWAITING_ACK ─┬─ ack success ─▶ ACKED ✅
                              │                                                      └─ ack failed ──▶ ACK_FAILED ⚠️
                              │                        └─(http_2xx 模式)────────────▶ ACKED ✅
                              ├─ 429/5xx/网络错误 ─▶ RETRYING ──到期──▶ PENDING（循环，attempts+1）
                              └─ 4xx(除429)/重试耗尽 ─▶ DEAD ❌
AWAITING_ACK 超时未回执 ──▶ 告警 + 保持滞留（人工处理，v1.1 提供自动重投递）
```

对外暴露：`PENDING / RETRYING / DELIVERED / AWAITING_ACK / ACKED / ACK_FAILED / DEAD`（`IN_FLIGHT` 为内部态）。

## 4. 系统边界

### 4.1 本系统解决

- 多供应商 API 差异的归一化受理（统一入口模型）
- 通知的持久化、异步投递、失败分类重试、死信
- **送达确认**：回执接收通道 + 按供应商的确认模式配置（D1）
- 生命周期状态查询与告警输出

### 4.2 明确不解决（及理由）

| 不解决 | 理由 |
| --- | --- |
| 下游返回值实时透传 / 主动回调业务系统 | 业务方不消费返回值（作业明确）；状态查询接口已覆盖其诉求 |
| 跨通知严格排序 | 场景无顺序依赖；排序约束会显著限制并行度，代价大于收益 |
| 通知内容模板引擎、字段映射 DSL | 透传 Body 已覆盖 MVP；模板化属 v2 |
| 认证凭证托管（OAuth 刷新等） | 安全合规专项，MVP 由业务方在 Header 携带 |
| 多实例水平扩展、削峰队列 | 单机 SQLite 已达 MVP 量级 1~2 个数量级以上；演进路线见技术文档 §6 |
| ACK_FAILED / 死信的自动重放 | v1.1 提供重放接口；MVP 人工处理 + 告警 |

## 5. 用户故事

1. 作为业务系统开发者，我希望用一个统一 API 提交通知，而不必关心供应商 API 差异，以便降低对接成本。
2. 作为业务系统开发者，我希望提交通知后立即拿到受理回执（而非等待供应商响应），以便主流程不被外部延迟阻塞。
3. 作为业务系统开发者，我希望重复提交同一事件不产生副作用，以便网络重试是安全的。
4. 作为业务系统开发者，我希望查询通知处于「已投递/待回执/已送达/失败」哪个阶段，以便向运营准确答复"广告系统到底生效没有"。
5. 作为对接供应商的技术人员，我希望通过回执接口确认通知的业务处理结果，以便 NotifyHub 能区分"网关收到"与"业务生效"。
6. 作为业务系统开发者，我希望供应商挂了数天后恢复时通知仍能送达，以便不用人工补发。
7. 作为运维人员，我希望重试超过 2 小时未成功时收到告警，以便及时感知供应商故障。
8. 作为运维人员，我希望死信与回执失败的通知可检索、可导出，以便人工介入处理。
9. 作为运维人员，我希望 AWAITING_ACK 长期滞留的通知有告警，以便发现"供应商不回执"这类隐性故障。

## 7. 验收标准（摘要）

- 受理接口**事务落库后**才返回 202；同一 `idempotency_key` 重复提交返回首次结果且不产生新记录；
- 下游 5xx/超时/网络错误触发 D3 退避重试；4xx（除 429）不重试直接死信；
- `callback` 模式下 2xx 仅置 `DELIVERED`，收到 ack 后才置 `ACKED`；`http_2xx` 模式 2xx 直接置 `ACKED`；
- ack 超时滞留与死信触发对应告警（告警通道 MVP 为日志 + 指标点，具体通道接入属部署项）；
- 进程重启后未完成任务继续投递；状态查询返回与 §3.3 状态机一致。
