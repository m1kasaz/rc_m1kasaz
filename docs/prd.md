# PRD：企业内部 API 通知系统（NotifyHub）

> 版本：v1.0（MVP）｜ 状态：已评审 ｜ 上游：AI Coding 作业《API 通知系统设计与实现》

---

## 1. 需求背景

### 1.1 业务背景

企业内部存在多个业务系统（广告引流注册、订阅付款、电商下单等），在关键业务事件发生时，需要调用**外部系统供应商**提供的 HTTP(S) API 完成通知，例如：

- 用户通过第三方广告系统引流并成功注册后，通知对应的广告系统；
- 用户订阅付款成功后，通知 CRM 系统更改 Contact 状态；
- 用户购买商品后，通知库存系统进行库存变更。

### 1.2 现状痛点

| 痛点 | 说明 |
| --- | --- |
| 供应商 API 碎片化 | 各供应商请求地址、Header、Body 格式各不相同，每个业务系统各自对接，重复建设 |
| 可靠性无保障 | 外部 API 可能超时、失败、长期不可用。业务系统通常"发完即忘"，失败即丢失 |
| 关注点错位 | 业务系统**不需要关心外部 API 的返回值**，只要求通知"稳定、可靠地送达"，但现状把可靠性负担压在了业务方 |

### 1.3 问题定义

> 设计并实现一个**内部通知服务**：接收业务系统提交的外部 HTTP 通知请求，并尽可能可靠地投递到目标地址，将"如何可靠送达"的责任从业务系统收拢到单一服务内。

## 2. 需求目标

### 2.1 功能目标（MVP 范围内）

1. **通知受理**：提供统一的 HTTP API，接收业务系统提交的「目标地址 + 请求模板 + 通知内容」，同步返回受理结果。
2. **可靠投递**：以**至少一次（at-least-once）**语义投递通知；对外部失败进行自动重试（指数退避 + 抖动）。
3. **状态可观测**：业务系统可查询某条通知的当前状态（待投递 / 投递中 / 成功 / 失败-重试中 / 死信）。
4. **幂等受理**：同一业务事件重复提交不产生重复副作用（以幂等键去重）。

### 2.2 非功能目标

| 维度 | 目标（MVP） |
| --- | --- |
| 可用性 | 接收接口同步处理，目标端失败不影响受理（快速失败返回受理回执） |
| 持久性 | 通知在受理后先持久化再返回，进程重启不丢任务 |
| 性能 | 单实例支撑 ≥ 100 TPS 受理峰值（MVP 量级，非考核重点） |
| 可运维 | 投递成功率、重试次数、死信量可观测（日志 + 指标点） |

### 2.3 投递语义决策

**选择：至少一次（at-least-once），不做恰好一次（exactly-once）。**

判断依据：

- 通知下游是外部系统，跨系统边界无法提供分布式事务，exactly-once 在物理上不可达；
- 业务系统不消费返回值，重复投递的代价由"幂等键 + 下游自行去重"承担；
- at-least-once 只需"持久化 + 重试"即可实现，复杂度显著低于基于去重表的 exactly-once 伪装。

## 3. 系统边界

### 3.1 本系统解决

- 多供应商 API 差异的归一化受理（统一入口模型）
- 通知的持久化、异步投递、失败重试、死信处理
- 通知生命周期的状态查询与基础可观测性

### 3.2 本系统明确不解决（及理由）

| 不解决 | 理由 |
| --- | --- |
| 下游返回值透传 / 回调业务系统 | 作业明确"业务不需要关心外部 API 返回值"；引入回调会引入业务方可用性耦合，v1 不做 |
| 跨通知的严格排序保证 | 广告→CRM 类场景无顺序依赖；排序保证会显著限制并行度，代价大于收益 |
| 通知内容模板引擎、字段映射 DSL | MVP 只需透传 Body；模板化是真实需求但属 v2 演进项 |
| 认证凭证托管（OAuth token 刷新等） | MVP 中由业务方在 Header 中直接携带凭证；凭证托管涉及安全合规，独立专项 |
| 多租户限流配额 | 内部系统阶段无此诉求 |
| 多实例水平扩展 | MVP 单实例 + 单 worker；演进路线在技术文档中说明 |

## 4. 用户故事

1. 作为业务系统开发者，我希望用一个统一 API 提交通知，而不必关心供应商 API 差异，以便降低对接成本。
2. 作为业务系统开发者，我希望提交通知后立即拿到受理回执（而非等待下游响应），以便我的主流程不被外部系统延迟阻塞。
3. 作为业务系统开发者，我希望重复提交同一事件的通知不会产生副作用，以便我可以安全地重试我的调用。
4. 作为业务系统开发者，我希望随时查询通知状态，以便向运营/客服说明"广告系统到底收到没有"。
5. 作为业务系统开发者，我希望外部系统挂了之后通知最终仍能送达（一旦恢复），以便不用人工补发。
6. 作为运维人员，我希望投递失败自动重试且次数有限，以便故障不会无限放大。
7. 作为运维人员，我希望重试耗尽的通知进入死信并可被检索，以便人工介入处理。
8. 作为运维人员，我希望有投递成功率等指标，以便评估各供应商 API 的健康度。

## 6. 验收标准（摘要）

- 受理接口在收到合法请求后 **先持久化、后返回** 受理回执；
- 下游 5xx/超时/网络错误触发自动重试，重试间隔指数退避（如 1m → 5m → 30m → 2h，上限后进入死信）；
- 同一 `idempotency_key` 重复提交返回首次受理结果，不产生新任务；
- 进程重启后未完成任务可继续投递；
- 状态查询接口返回的生命周期状态与文档 §状态机一致。
